# Соглашения

**Файл поставляется скиллом research-log. Не редактируй его вручную:**
`upgrade.py` перезаписывает файл целиком. Правила проекта записывай в
[`conventions-local.md`](conventions-local.md) — его скилл не изменяет.

## Где что искать

| Что нужно | Где смотреть |
|---|---|
| цель проекта и её направления, в том числе оставленные | [`vision.md`](vision.md) |
| стек, окружение, структура кода, внешние инструменты, тесты | [`conventions-local.md`](conventions-local.md) |
| что проверяется сейчас | [`hypotheses/_index.md`](hypotheses/_index.md) |
| что уже установлено | [`findings/_index.md`](findings/_index.md) |
| что зафиксировано и почему | [`decisions/_index.md`](decisions/_index.md) |
| что запускали и на каких данных | `experiments/` |
| как проверяли инструменты | `technotes/` |
| как что-то поставить, пересобрать, запустить | [`protocols/_index.md`](protocols/_index.md) |
| над чем идёт работа | трекер задач; `tasks/`, если в проекте есть скилл task-tracker |

## Куда класть новое

Проверяй условия по порядку. Документ относится к первому подходящему типу.

1. Прогон, результат которого говорит что-то о предмете исследования: о модели,
   методе, данных → эксперимент. Основной расчёт проекта, например обучение и
   оценка модели, относится сюда всегда. Прогон, в котором есть сомнения, тоже.
   Его числа не пишутся в задачу, в чат или в ячейку блокнота.
2. Прогон, проверявший инструменты проекта: скорость кода, совпадение с другой
   библиотекой, чтение файлов или признаков → техническая заметка, даже если её
   числа потом сравнивают. Если по ней сделан выбор, запиши ещё и решение.
3. Утверждение, установленное проектом и верное шире одного прогона → находка.
   Порог: оно влияет на будущие решения. В поле `class` укажи, чем оно
   допущено: `empirical` — прогонами, `formal` — доказательством, `review` —
   поиском по литературе, `analytical` — разбором известных свойств.
4. Утверждение, которое предстоит проверить → гипотеза. Переведи её в `active`
   и запиши критерий опровержения.
5. Фиксация определения, порога или среза данных → решение.
6. Порядок действий, который придётся повторить → протокол. Установка
   инструмента с его ловушками, пересборка метрик, сборка отчёта, методика
   измерения, по которой идёт прогон.
7. Остальное → трекер задач. Сюда же smoke-тесты и отладочные прогоны.

Заголовок и текст документа — на языке проекта. Имя файла — всегда на
английском: передай `--slug` из трёх-четырёх слов. Без него скрипт
откажется создавать документ с неанглийским заголовком.

## Что делать в каждой ситуации

| Ситуация | Действие |
|---|---|
| предстоит полный прогон | сначала пробный прогон на малом срезе: дерево может быть грязным, в журнал он не пишется. Если он прошёл, закоммить всё, что участвует в прогоне: код, конфиг, скрипт замера. Посторонние правки могут остаться незакоммиченными. Запомни SHA. Закоммитить после прогона нельзя: `commit:` укажет на код, с которым прогон не запускался, а повторять прогон дорого. Прямо перед полным прогоном сделай rebase ветки на main; MR открывай сразу после записи прогона. Каждый rebase после записанного прогона грозит записью, под которой изменился код, поэтому дальше ветку ребейзят только для слияния. Прогон, которому не нужен собственный код, запускается на коммите из main, без своих коммитов поверх: такая запись указывает на коммит, который не затронет никакой rebase, в каком бы порядке ни вливались MR |
| прогон завершился | эксперимент записывает `record_run.py`, техническую заметку — он же с `--kind technote`. Если HEAD после запуска сдвинулся или в дереве остались посторонние правки, передай `--commit <SHA перед прогоном>`. Вручную блок `run:` не заполняется: это сведения о воспроизводимости, которые никто не проверял |
| ветку переписали rebase, squash или amend, локально или на сервере | если задан `run_paths`, хук post-rewrite уже перенёс записи, у которых по этим путям ничего не изменилось. `rebase_runs.py` покажет остальные — эксперименты, технические заметки и находки — и что изменилось. `--same --paths <что использовал прогон>`, если этот код не менялся; `--keep`, если менялся: старый коммит получит тег, тег нужно запушить. Либо повтори прогон и запиши его с `corrects:`. Обновлённые записи закоммить. Вручную `run.commit` и `origin.commit` не правятся |
| одновременно готовы несколько MR | сначала вливаются те, что ничего не меняют в `run_paths`. Правка кода, влитая после чужих прогонов, их записи не задевает; влитая до них — оставляет все записи в ещё не влитых ветках с кодом, которого в main уже нет. Правка кода, нужная нескольким людям, вливается первой отдельным маленьким MR, и остальные ребейзятся на неё прямо перед своими прогонами |
| переписанная ветка изменила код, на который ссылается запись, и разбирается агент | по умолчанию `--keep`: он ничего не утверждает. `--same --basis` — только с доказательством, записанным в основание: пробный прогон на малом срезе дал одинаковый результат на обоих коммитах (укажи команду), или изменённые файлы не входят в загруженные прогоном (укажи, как это установлено). Прочитанный diff доказательством не считается: покажи его пользователю, решает он. Push тега или переписанной ветки — с согласия пользователя |
| запись, под которой изменился код, прогоняют повторно | те же числа: новая запись не нужна; `rebase_runs.py <id> --same --basis "повторный полный прогон на <sha> воспроизвёл числа: <какие числа, было → стало>, <команда>"`. Другие числа: новая запись с `corrects:`, и пересмотри то, что ссылается на старую. Коммит исправленной записи больше не проверяется; её тег остаётся, пока его не удалят |
| нужно воспроизвести прогон или находку | разверни коммит из записи рядом с рабочей копией, а не в ней: `git worktree add ../repro-<id> $(grep -m1 '^  commit:' docs/*/<id>-*.md | awk '{print $2}')`. Коммит берётся из frontmatter записи, а не из её места в `git log`: запись, влитая после чужого кода, по-прежнему указывает на код, на котором шёл прогон. Когда закончишь — `git worktree remove ../repro-<id>` |
| коммит нужно сохранить после переписывания ветки | тег — `research-log/<id>`, его ставит `rebase_runs.py --keep` и больше ничто. Собственные теги проекта в `research-log/` не кладут |
| стало понятно, от каких путей зависит результат прогонов | перечисли их в `run_paths` в `.research-log.md` |
| сделан клон репозитория | один раз `rebase_runs.py --install-hooks`. Хук post-rewrite запоминает, какой коммит чем заменён; хук pre-push не даёт запушить ветку, в которой запись осталась без своего коммита |
| прогон читает данные | версию данных задаёт проект, а не журнал. Если данные под DVC или похожим инструментом, lock-файл лежит в git и `run.commit` задаёт их версию вместе с кодом. Если нет, источник и версия данных пишутся в протокол или в текст документа. `record_run.py` файлы не хеширует |
| гипотеза взята в работу | переведи статус в `active`, заполни критерий опровержения, проставь `criterion_set`. В этом порядке и до первого прогона |
| гипотеза разрешена | запиши находку, поставь `status: resolved` и `finding:`. Опровержение тоже даёт находку |
| вопрос оказался поставлен неверно | `status: recycled`, `successor:` |
| в задаче появилось число | перенеси его в эксперимент или техническую заметку, в задаче оставь ссылку |
| непонятно, эксперимент ли это | запиши эксперимент. Если такое сомнение повторяется, один раз спроси пользователя и запиши класс прогонов в `conventions-local.md` |
| в эксперименте или технической заметке найдена ошибка | создай **новый** документ того же типа с полем `corrects:`. Исправлять старый нельзя |
| изменилось определение | создай новое решение взамен старого. Исправлять старое нельзя |
| прогон использовал зафиксированный порог или срез данных | укажи это решение в поле `rests_on` эксперимента |
| прогон шёл по записанной процедуре | укажи протокол в поле `under` эксперимента |
| выбор сделан по технической заметке или эксперименту | укажи их в поле `based_on` решения |
| стало понятно, как что-то ставится, запускается или собирается | запиши протокол, если это понадобится снова |
| определился стек, структура кода или версия инструмента | запиши строку в `conventions-local.md`, до кода, который на неё опирается |

## Правила с автоматической проверкой

| Правило | Чем проверяется |
|---|---|
| Прогон при незакоммиченных изменениях отклоняется; из каталога журнала не мешают только `.md` | `record_run.py` |
| `--commit` принимает только существующий коммит | `record_run.py` |
| В поле `date:` — дата самого раннего прогона, а не дата создания документа | `record_run.py` |
| Каждый `run.commit` и `origin.commit` находки этого проекта — предок HEAD или удерживается тегом записи | `check.py`, хук pre-push |
| `--same --paths` переносит `run.commit`, только если по этим путям нет изменений | `rebase_runs.py` |
| Гипотеза в статусе `idea` не ссылается на эксперименты | `check.py` |
| Каждый упомянутый эксперимент датирован позже `criterion_set` | `check.py` |
| Каждое решение из `rests_on` принято не позже прогона | `check.py` |
| Каждый протокол из `under` создан не позже прогона | `check.py` |
| Находка класса `empirical` называет в `origin` хотя бы один эксперимент или техническую заметку | `check.py` |
| Гипотезы и эксперименты не ссылаются на технические заметки | `check.py` |
| Каждый документ из `based_on` решения датирован не позже решения | `check.py` |
| Идентификаторы уникальны, корректны и совпадают с именами файлов | `check.py` |
| Имя файла английское: неанглийский заголовок без `--slug` отклоняется | `new.py`, `record_run.py` |
| Индексы сгенерированы и не устарели | `index.py --check` |

`check.py` запускается перед коммитом. Других проверок скилл не добавляет; что
ещё блокирует коммит в этом проекте, записано в `conventions-local.md`.

## Правила без автоматической проверки

Поля без читателя. Если колонку, поле или раздел не использует ни человек, ни
скрипт, удали их или добавь проверку в `check.py`.

Дублирование чисел. Каждое число хранится в одном эксперименте или
технической заметке. Находка может повторить числа, на которых основана.
Остальные документы ссылаются на источник.
